###  Unreleased
<!-- lane: rust-core -->
- **Bugfix (Rust): a URL containing non-ASCII digits could crash the CLI.** A path segment or query value mixing ASCII digits with digits from another script (`https://x.com/1०००००००`, `?d=2024-٠١-١٥`) panicked in the classifier (exit 101). Rust now treats "digit" as ASCII `0-9`, as Ruby always has, so those values are plain literals.
- **Bugfix (Rust): non-ASCII digits and spaces classified differently from Ruby.** `?v=1.٥` was `{float}` and `?v=v𝟎` was `{version}` (Ruby: literal); `?u=http://x.com/a<NBSP>b` stayed literal (Ruby: `{url}`, since only ASCII whitespace ends a URL); `registrable_domain("١.٢.٣.٤")` was treated as an IPv4 literal. Rust now matches Ruby on all of these.
- **Bugfix (Rust): `--host reg` merged unrelated sites whose hostnames end in a dot.** `api.foo.com.` and `api.bar.com.` both keyed as `com.`; they now key as `foo.com` and `bar.com`, as in Ruby. A corpus built with `--host reg` from such hosts keeps its old `com.` clusters until rebuilt with `--host reg --reinfer`.
- **Bugfix (Rust): hosts ending a word in capital sigma lowercased differently from Ruby.** `https://ΑΣ-x.com/` parsed to host `ας-x.com` (final-form sigma); it is now `ασ-x.com`, as in Ruby, so both runtimes cluster such hosts under the same key.
- **Bugfix (Rust): `kind_distribution` dropped values with an unrecognized extension.** A `file` param seen as `b.pdf` ×3 and `c.zzz` reported `{"document":0.75}`; it now reports `{"document":0.75,"unknown":0.25}` like Ruby. Library consumers: `FileKind` gains an `Unknown` variant, used only as that bucket (`file_kind` never returns it).
- **Bugfix (Rust): a numeric param with a 310+ digit value lost its range.** The value overflowed to infinity, so `max`/`avg` came out as `null` in `cluster --json`. Such values still count toward the param's observations, but `min`/`max`/`avg` now cover only finite values (Ruby adopts the same rule).
- **Breaking (Rust library API): classifier and cluster types are narrowed.** No CLI change. What to do: (1) `SegmentType`, `FileKind`, `Cluster`, `ParamSummary`, `SegmentPositionStat` and `PositionStats` are `#[non_exhaustive]` — add a `_ =>` arm when matching `SegmentType`/`FileKind`, and create `Cluster`/`PositionStats` with `::new` rather than struct literals. (2) `SegmentType::Custom` now wraps a `CustomType` instead of `&'static str`, so `SegmentType::Custom("integer")` no longer compiles (it silently differed from `SegmentType::Integer`); get a custom type from `segment_type_from_name("ghp")`, which returns the built-in variant for built-in names, and read its name with `.as_str()`. Also new: `Cluster`, `ParamSummary`, `PositionStats`, `SegmentPositionStat`, `Identifier` and `OrderedMap` implement `PartialEq`.

<!-- lane: ruby -->
- **`-N` / `--no-hints` now works with a corpus** (the default). It was silently ignored whenever a corpus was in play; placeholders now show the type (`{integer}`), and a slot the corpus learned is variable renders `{value}`.
- **The corpus changes a URL's shape only where it has evidence.** A position or query param observed fewer than 5 times renders exactly as `--no-corpus` would. Previously one observation was enough to print a raw `v1` / `abc-123` / `usd` instead of `{version}` / `{post_id}` / `USD`, and corpus mode skipped param-name hints (`?phone=unknown` → `{phone}`). If you script against corpus-mode `-n` output, expect those first-sighting lines to change.
- Dates and currencies always print in canonical form (`2024-01-15`, `USD`), with or without a corpus — corpus mode no longer renders `{currency}`. Currency upcasing is ASCII-only (`uſd` is not `USD`).
- **Positional files no longer need `./`.** `iriq access.log` reads the file (it used to parse as the host `https://access.log/` and, with `--stats`, report 0 observations). Rule: an argument that names an existing file is read as a file, unless it contains `://`. A missing path-like argument (`./x`, `/x`) or `cluster` file now says `iriq: no such file: PATH` (exit 1, JSON code `file_not_found`) instead of a parse error or backtrace.
- Invalid UTF-8 input is a clean error (`iriq: stream did not contain valid UTF-8`, exit 1, JSON code `invalid_utf8`) instead of a Ruby backtrace. Both errors honor `--json` in both runtimes.
- Numeric params too long to be finite no longer crash `cluster` (JSON and human views) or lose the batch before a JSON corpus is saved; they still count toward type/value counts but are left out of min/max/avg.
- `--host` now applies with `-C` / `--no-corpus`; it was silently ignored there, so `-C --host reg cluster` kept subdomains apart.
- `--host bogus` reports `invalid argument: --host bogus (expected full|registrable|reg|none)` — no doubled `--host`, and the `--host=bogus` form keeps the explanation.
- `--explain`: an already-canonical date or currency shows its value, agreeing with the normalized line, instead of `{date}` / `{currency}`; explain JSON omits `host` for IRIs without one rather than emitting `null`.
- `--propose-recognizers` never names a proposal after a built-in type: `literal_` proposes `literal_id`. Activating the old name turned every matching value into a fixed literal. Recognizers already activated under a built-in name stay as they are; `--reset` or a fresh corpus clears them.
- **Corpus files iriq can't safely use are refused, not clobbered or crashed on.** A `.json` corpus that isn't a JSON object with at least one corpus key (or `{}`) exits 1 and is left untouched (`iriq: corpus PATH: not an iriq corpus (no corpus keys at the top level)`, or `corpus PATH: not valid JSON`). A SQLite corpus written by a newer iriq (higher `schema_version`) exits 1 asking you to upgrade (`corpus PATH: schema version N is newer than this iriq supports (4); upgrade iriq`). A write SQLite refuses, such as a read-only `.db`, exits 1 with `corpus PATH: attempt to write a readonly database` instead of a Ruby backtrace. Every corpus failure uses this `corpus PATH: reason` form, and under `--json` the error code is `corpus_error`, in both runtimes. JSON corpus saves use a writer-unique temp file, so concurrent saves no longer crash — but a `.json` corpus is still last-writer-wins; use `.db` for concurrent writers.
<!-- /lane: ruby -->
<!-- lane: ruby-perf -->
- **Ruby, SQLite corpora: `-n` with a corpus does far less work per URL.** Normalizing a URL read every value tracked at each of its path positions and its whole cluster, observing one reloaded the whole cluster, and each new value re-counted its position's values; now each reads only what it uses. Output is unchanged. 10k URLs into a fresh `.db` went from ~2400G to ~48G instructions (157s → 3s of CPU on the benchmark box).
- Ruby: a corpus file iriq can't open, read or write is a clean `iriq: corpus PATH: reason` error (exit 1, `corpus_error` under `--json`) instead of a backtrace — a `.db` that isn't a database, an unreadable or directory `.json`, a corpus directory that can't be created, a failed JSON save. The reasons match the Rust CLI's (`file is not a database`, `Permission denied (os error 13)`).
- Ruby, SQLite corpora: `--reinfer` (and `--activate-above`, which reinfers) waits for concurrent writers instead of failing with `corpus PATH: database is locked`, as the Rust CLI does. Every Ruby corpus transaction now takes the write lock when it begins.
- Ruby: input iriq can't read — a file argument without read permission, stdin that is a directory — is a clean error like the Rust CLI's (`iriq: Permission denied (os error 13)`, exit 1, JSON code `read_error`) instead of a backtrace. Invalid UTF-8 keeps its own `invalid_utf8` code.
- `--propose-recognizers --activate-above F` with nothing to activate now says `no proposals at or above confidence F`; it said "coverage", but `F` is a confidence threshold.

<!-- lane: rust-storage -->
- **Rust library: breaking — corpus operations return `iriq::Error`.** What you must do: replace `std::io::Error` / `ParseError` in your `Corpus` error handling with `iriq::Error` (or `iriq::Result<T>`). It is `#[non_exhaustive]` with `Parse`, `Io`, `Corrupt`, `Unsupported`, and (with the `sqlite` feature) `Sqlite` variants; every storage variant carries the corpus `path`, and `Display` names the corpus while the cause is in `source()`. `ParseError`'s field is now private (use `.message()`), its `Display` drops the `iriq: ` prefix, and `Corpus::open` / `save` take `impl AsRef<Path>`. The pure functions (`parse`, `normalize`, `trace`, `explain`) still fail only with `ParseError`.
- **Bugfix (Rust): SQLite write failures were silently discarded.** A read-only, full, or otherwise failing `.db` corpus accepted every observation, wrote nothing, and the CLI exited 0 — so a cron job could lose data indefinitely without a sign. Every storage write now reports its failure: the CLI exits 1 with `iriq: corpus <path>: <cause>` (e.g. `attempt to write a readonly database`), and the library returns `Error::Sqlite`. Library consumers: `Corpus::observe_iri` now returns `Result<()>`, and `Corpus::batch` takes a closure returning `Result<T>` — on SQLite the batch commits on `Ok` and rolls back on `Err`, matching Ruby.
- **Bugfix (Rust, SQLite): a panic could wedge a corpus for the rest of the process.** A panic inside `Corpus::batch` left its transaction open, so every later "successful" write was rolled back when the corpus closed; a panic while the connection lock was held poisoned it and made every later call panic; and iterating the corpus while normalizing against it deadlocked. `batch` now rolls back on panic before the panic continues, writers no longer take the lock, and callbacks run after it is released.
- **Bugfix (Rust): `Corpus::save` could destroy a live SQLite corpus.** It compared path strings, so saving to another spelling of the corpus's own file (`dir/./c.db`) overwrote the database with a JSON export. `save` now resolves both paths and flushes in place when they name the same file. Exporting to a SQLite extension (`save("backup.db")`), which used to write JSON that no build could reopen, now returns `Error::Unsupported` and writes nothing: exports are JSON, so use a `.json` path.
- **Bugfix (Rust): re-activating a recognizer piled up duplicates.** Activating the same proposal N times registered N copies on the live classifier and re-ran `reinfer` N times, although only one was persisted. Activation is now idempotent. A corpus's classifier is rebuilt from its stored activations, so a live corpus and the same corpus reopened from disk classify identically.
- **Bugfix (Rust): IP addresses normalized as `{ipv4}`/`{ipv6}` whenever a corpus was in play (the default).** `iriq -n https://a.com/hosts/10.0.0.1` printed `/hosts/{ipv4}` with the default corpus but `/hosts/{ip}` with `-C`, and Ruby always prints `{ip}`. The corpus path now uses the same `{ip}` placeholder for path segments and query values.
- **Breaking (Rust library API): the public surface is now a deliberate list.** No CLI change. What you must do:
  - **Import from the crate root.** The module paths (`iriq::classifier::…`, `iriq::corpus::…`, `iriq::storage::…`, and the rest) are gone.
  - **Stop using removed items.** Gone: the `Storage` trait, `open_storage` and the storage backends; `Corpus::storage()`, `storage_mut()`, `new_with_classifier`, `stats_for`, `max_values_per_position`; the `Corpus.classifier` and `Corpus.host_strategy` fields (use `set_host_strategy`); `DEFAULT_CLASSIFIER`, `SegmentClassifier`, the recognizer types and `SynthesizedRecognizer`; `Clusterer`, `ClusterKey`, `cluster_key_for*` and `ExplainEntry`; `Event`, `Observation`, `Shape`, `ShapeRenderOptions` and `PathShape`; `derive_hints*`, `NormalizationEvidence`, `NullEvidence` and `normalize_identifier_with_evidence`; `explain_identifier`; the classifier helpers (`display_type`, `color_kind`, `file_kind`, `param_name_hint`, `canonical_currency`, `canonical_date`); `DEFAULT_MAX_VALUES_PER_POSITION` and the corpus tuning constants. These let callers mutate process-wide classification (registering a recognizer on one corpus changed every corpus and `normalize()`) or desynchronize a corpus from its own source log.
  - **Update changed signatures.** `normalize_identifier(&iri, hints)` and `trace_identifier(&iri, hints)` no longer take a classifier. `cross_host_shapes(&corpus, n)` is now `corpus.cross_host_shapes(n)`. `Corpus::activate_proposal` returns `Result<()>`, and `activate_proposals_above` returns the `RecognizerProposal`s it activated.
  - **Adjust for `#[non_exhaustive]`.** It now covers `Extractor`, `Identifier`, `Kind`, `Position`, `PositionScope`, `Classification`, `CorpusEntry`, `HostStrategy`, `CrossHostShape`, `RecognizerProposal`, `ProposalOptions`, `SegmentHint`, `TraceResult` and `TraceRow`. Build `Extractor` and `ProposalOptions` from `::new()` / `::default()` and assign fields, and add a `_ =>` arm when matching these enums.
  - **New:** `Corpus` implements `Debug`, and `segment_type_from_name` and `CustomType` are exported at the root.
- **Bugfix (Rust, JSON corpora): three ways a `.json` corpus failed badly.**
  - Concurrent saves to one file crashed (`No such file or directory`), because every writer renamed the same `<path>.tmp`. Each write now uses its own temp file. The last writer still wins: treat a `.json` corpus as single-writer, or use `.db` for concurrent observers.
  - A JSON file that isn't a corpus opened as an empty corpus and was overwritten on save. Opening an object with none of the corpus's top-level keys now fails with `iriq: corpus <path>: not an iriq corpus (no corpus keys at the top level)` and exits 1, leaving the file untouched. An empty object `{}` is still an empty corpus.
  - A corpus in a directory that doesn't exist opened fine and failed only at save, with an error that didn't name the file. It now fails at open with `iriq: corpus <path>: No such file or directory (os error 2)`.
- **Bugfix (Rust, SQLite corpora): a corpus written by a newer iriq was opened anyway.** Its stored schema version was recorded but never checked, so an older binary could read and write a schema it doesn't understand. Opening one now fails before anything is written, with `iriq: corpus <path>: schema version <n> is newer than this iriq supports (4); upgrade iriq`, and exits 1. Corpora without a recorded version are stamped as before.
- **Rust crate packaging.** No behavior change.
  - The crate declares `rust-version = "1.85"`, checked against the current lockfile.
  - docs.rs builds with all features and labels the SQLite-only error variant.
  - The published crate no longer ships integration tests, which read fixtures from the repository and could only fail outside it.
  - The CLI detects a terminal with `std::io::IsTerminal` instead of an `unsafe` Unix-only `isatty` call.

<!-- lane: rust-cli -->
- **Bugfix (Rust): the human cluster view printed some numbers wrong.** A numeric param past 2^63 (`?v=18446744073709551616`) printed `9223372036854775807..9223372036854775807  avg 9223372036854775807`; it now prints the exact value, as Ruby does (`18446744073709551616..99999999999999991611392`). Averages and ranges also round and print like Ruby's `format_num` everywhere else: a non-whole value that rounds to a whole number keeps its `.0` (`avg 3.0`, was `avg 3`), a rounded `-0.004` prints `-0.0`, `1.005` rounds to `1.01`, and values past 15 digits use Ruby's `e+15` notation. `--json` output is unchanged.
- **Bugfix (Rust): `--reset` left a crashed save's temp files behind.** A JSON corpus saves through its own temp file, `<path>.<pid>.<n>.tmp`, but `--reset` removed only `<path>.tmp`, so a save killed mid-write left files nothing ever cleaned up. `--reset` now removes those as well as the corpus, its `-wal`/`-shm` sidecars and `<path>.tmp`, and nothing else.
- **Bugfix (Rust): iriq kept running after its reader went away.** Every stdout write ignored its error, so `iriq -C -n big.log | head -1` read the whole file and `tail -f access.log | iriq -n | head -1` never exited. A closed stdout now ends iriq at its next write, silently and with status 141, the status Ruby's CLI reports when SIGPIPE kills it; a corpus still saves everything read up to that point. What to check: a `set -o pipefail` pipeline ending in `| head` now fails with 141 where it used to succeed. Any other stdout failure exits 1 with `iriq: stdout: <cause>` (under `--json`, a `stdout_error` envelope) instead of exiting 0 with the output lost.
- **Bugfix (Rust): `-n`/`-c`/`-p`/`-e` printed nothing until stdin closed whenever a corpus was in use (the default).** `tail -f access.log | iriq -n` printed nothing, and `iriq -n big.log | head -1` read the whole file before its first line. Per-IRI sections now stream with a corpus too. Input is observed in chunks of whatever lines have arrived; each chunk commits before its lines print, so a killed `iriq` never prints a line its SQLite corpus lost (a JSON corpus, as before, is written only at exit). What changes in the output: each line now renders from the corpus as it stood when that line was observed, not from the finished corpus. With a warm corpus the output is the same; with a cold one, the first lines of a run print their literal values until the corpus has seen enough to use a placeholder. Only `--json` (one array) still waits for the end of input to print.

<!-- lane: perf -->
- **Performance (Rust): corpus-informed normalization no longer slows down as the corpus grows.** No action needed; output is byte-for-byte unchanged. `iriq -n` with a corpus (the default) read every value and example the corpus held for a route to shape each URL, so each line cost more than the last. Piping 20,000 URLs of one route through `iriq -n` into a fresh corpus took about 5 minutes with `.db` and 20 s with `.json`; it now takes about 6 s and 0.2 s. It now reads only the counts classification uses.
- **Performance (Rust, SQLite): observing a route the corpus already knows no longer scans every route.** No action needed. Each observation looked through all of a `.db` corpus's routes to number a new one, even when the route wasn't new; now only a route's first observation does. 20,000 URLs over 1,000 hosts went from about 1 s to 0.4 s.
- **Performance (Rust, SQLite): a new value in a busy URL slot no longer re-counts the slot.** No action needed. To enforce the per-slot value cap, each value a `.db` corpus hadn't seen in a slot counted every value already there, up to the cap of 5,000. Inside a batch the corpus now remembers the count, and drops it whenever another process has written to the file since. Observing 20,000 URLs of one route with `--stats` went from about 6 s to 0.5 s, and `-n` from about 6 s to 1 s.
- **Bugfix (Rust, SQLite): an observation that failed part-way stayed half-recorded.** A write failing mid-observation (a full disk, a lock timeout) left the counts it had already bumped in a `.db` corpus, so its views no longer matched its source log until `--reinfer`. Each observation is now one transaction, as in Ruby, and a failure keeps none of it. Library consumers: a `Corpus::batch` inside another `batch` (including `observe` inside `batch`) joins the outer one, so only the outermost commits or rolls back. An observation's error swallowed inside a batch keeps its writes.
<!-- /lane: perf -->

<!-- lane: port -->
- **Ruby: `-n`/`-p`/`-c`/`-e` on piped input now print each URL the way single-input mode does.** Rule, for both runtimes: each extracted URL is observed, then rendered from the corpus as it stands at that moment. With `-C` there is no corpus, so output is mechanical. Before, Ruby always rendered piped `-n` mechanically, even with a corpus, and piped `-e` printed only the `# URL` header with no trace (`[]` under `--json`). What changes for Ruby users: with a warm corpus, piped `-n` now shows the corpus's shapes, just like `iriq -n URL`. With a cold corpus, a slot stays literal until it has been seen 5 times.
- **Ruby: `--reset` now also removes a crashed JSON save's temp files, like Rust.** Both runtimes now save a `.json` corpus through `<path>.<pid>.<n>.tmp`. `--reset` removes the corpus, its `-wal`/`-shm` sidecars, `<path>.tmp`, and any `<path>.<pid>.<n>.tmp`. Nothing else is touched.
- **Rust: corpus-mode `-n` now follows the rules in the ruby-lane notes above.** `-N` is honored with a corpus. A position or param seen fewer than 5 times renders exactly as `-C` would. Dates and currencies always print canonically. Rust used to print `usd?currency={currency}&phone=unknown` for a first sighting and `{user_id}` under `-N`. **Breaking (Rust library API):** `Corpus::normalize_identifier(&iri)` is now `normalize_identifier(&iri, hints)`, like the free `normalize_identifier`. Pass `true` for the old output.
- **Bugfix (Rust, SQLite): `--reinfer` could corrupt a corpus that other processes were writing to.** Reinfer read the observation log, cleared the views and replayed the log in separate steps, so another process's commits could land in between. It either exited 0 with views that no longer matched the log, or died part-way with `UNIQUE constraint failed: cluster_examples…` after the clear had already committed. Reinfer, including the one `--activate-above` runs, is now a single transaction, as in Ruby. Writers wait for it to finish. What to do: if you ran `--reinfer` against a `.db` that was being written to at the time, run `--reinfer` again once writes have stopped.

<!-- lane: rust-p2d -->
- **Breaking (Rust library API): every `Corpus` read returns `iriq::Result`.** What you must do: add `?` (or handle the error) on `normalize`, `normalize_identifier`, `explain`, `params_for`, `clusters`, `size`, `host_counts`, `path_length_counts`, `raw_shape_counts`, `fingerprint_counts`, `cross_host_shapes`, `propose_recognizers`, `observed_iri_count` and `activated_recognizer_count`. `Corpus::normalize` now fails with `iriq::Error` (a parse failure is `Error::Parse`), and `explain` / `params_for` return `Error::Parse` for input that doesn't parse, as `observe` always has; they used to return an empty list. An in-memory corpus never fails a read, but the type doesn't know its backend.
- **Bugfix (Rust, SQLite): a corpus read that failed printed a plausible answer and exited 0.** A read SQLite refused (a row it couldn't decode, a table changed under the process) was treated as "no evidence" or skipped: `iriq -n` printed a mechanical shape, `--stats` left the row out of its counts, and some reads panicked. Every such read now exits 1 with `iriq: corpus PATH: <cause>` (JSON code `corpus_error`), like a failed write.
- **Breaking (Rust library API): `SegmentType` is no longer `Copy`.** What you must do: `.clone()` a `SegmentType` where you copied it out of a borrowed struct (`row.ty`, `hint.ty`), and match through a reference (`matches!(&t, SegmentType::Custom(c) if …)`). `SegmentType::as_str` and `CustomType::as_str` now return `&str` borrowed from the value instead of `&'static str`; call `.to_string()` to keep the name. Why: a custom type used to be an interned `&'static str` that was never freed, so every distinct custom type name a process read (from corpus files, or from activated recognizers) stayed in memory until exit (about 90 bytes for each 70-character name). A custom type now owns its name and frees it with the last copy.
- **Bugfix (Rust library, SQLite): a commit that failed without ending its transaction wedged the corpus.** When SQLite refused a `COMMIT` but kept the transaction open (a deferred constraint does this), every later observation failed with `cannot start a transaction within a transaction`, and other processes waited on a write lock that was never released until the `Corpus` was dropped. A failed commit now rolls back what it could not commit and returns the commit's error; the next batch starts clean.
- **Bugfix (Rust, SQLite): a running writer ignored recognizers another process activated.** `tail -f access.log | iriq -n` kept classifying with the recognizers it started with, so after `iriq --propose-recognizers --activate-above …` ran elsewhere, the stream still printed `/repos/{repo_id}/x` and wrote those clusters beside the new `/repos/{ghp}/x` ones. Each batch (each streamed chunk, or each observation outside a batch) now picks up activations committed before it began. It costs one small read only when another process has written since the previous batch. What to do: if a live writer overlapped an activation, run `--reinfer` once.
- **Bugfix (Rust): a numeric param's `avg` could differ between two runs over the same corpus.** Reopening a corpus rebuilds each numeric range from its stored values, and the sum was added up in hash-map order, so `cluster -j` printed `100000000000002.52` on some runs and `…2.53` on others. The sum now follows the order the corpus stores its values (sorted by value in a `.db`, file order in a `.json`), so the same corpus always reports the same `avg`.
- **Performance (Rust, SQLite): a new query-param value no longer re-counts the param's values.** No action needed. Each value a `.db` corpus hadn't seen for a cluster's param counted every value already tracked there (up to 5,000), as path slots used to before the per-batch count. Params now share that count. Observing 20,000 URLs with unique `?q=` values with `--stats` went from 2.2 s to 0.2 s, and `-n` from 17 s to 15 s.
- A `.db` corpus that can't be opened (a directory, or a new file in a read-only directory) names its path once: `iriq: corpus PATH: unable to open database file`. Rust printed the path again after the reason.
- `--propose-recognizers --activate-above F` with nothing to activate now says `no proposals at or above confidence F`; it said `coverage`, but `F` is compared against each proposal's confidence. Same message in both runtimes.

###  0.34.0  (2026-08-12)
- **Rust: SQLite is now an optional (default-on) feature.** `cargo install iriq`, the Homebrew formula, and the CLI are unchanged — `default = ["sqlite"]`. Library consumers who only need parsing, extraction, or normalization can now take `iriq = { version = "0.34", default-features = false }` and skip the bundled C SQLite build entirely (`rusqlite` is the crate's only non-Rust dependency). Without the feature, `open_storage` rejects `.db`/`.sqlite`/`.sqlite3` paths with a clear `Unsupported` error and the CLI's auto-default corpus becomes `default.json` instead of `default.db`; Memory and JSON backends are unaffected. No behavior change with default features, so Ruby parity and the shared schema are untouched. CI now gates the no-default-features build (test + clippy) so the configuration can't rot.

###  0.33.0  (2026-07-07)
- **New: end-to-end URL calibration corpus** — 160 messy real-world-shaped inputs (tokens, i18n, encoding damage, legacy endpoints, non-http schemes, garbage) with adjudicated expected templates at `spec/fixtures/calibration/urls.json`, generated by `script/build_url_calibration.rb`, asserted by both runtimes, and CI-gated for staleness. Building it caught the three fixes below.
- **Bugfix: opaque non-urn schemes were rewritten to `urn:` on normalize/canonical** — `mailto:support@foo.com` came back as `urn:support@foo.com`; same for `tel:`, `sms:`, `data:`, `blob:`, `magnet:`. The scheme is now preserved (both runtimes; cluster keys too).
- New `:font` file kind (`woff`/`woff2`/`ttf`/`otf`/`eot`), plus `m3u8` (video) and `map` (web) extensions — `Inter-Bold.woff2` now normalizes to `{file}` instead of `{font_id}`.
- **Bugfix (Rust):** out-of-range ports (`:99999`) were rejected where Ruby's deliberately lenient parser accepts them — the port field is now `Option<u64>` matching Ruby's nil-vs-integer semantics.
- **Bugfix (Ruby, SQLite backend):** rolling numeric stats (`min`/`max`/`avg` on numeric params) were never restored when loading a corpus from disk, so numeric ranges vanished from cluster output after a reopen — diverging from the Memory/JSON backends and from Rust. Now recomputed from tracked value counts on load; locked in by a new parity scenario and storage specs.

###  0.32.0  (2026-06-26)
- **Query params now climb a confidence ladder: constant → string → enum.** A param with a single observed value is a constant (rendered as its value); one that varies across free-form literal values is the new `string` type (renders `{string}`); a bounded, well-supported value set is `enum` (renders `{enum}`). - **New `confidence` score on every param** (`total / (total + 15)`): a 0–1 figure of how much evidence backs the classification, shown in the cluster view (`status  enum  conf 0.93  ...`) and the cluster JSON. The type is the guess; confidence says how sure.
